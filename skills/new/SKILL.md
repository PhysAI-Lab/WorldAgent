# New WorldAgent case

Arguments: `$ARGUMENTS` — the first word is the case directory; the rest is the user's exact scene request. If either is missing, ask for it.

1. Invoke the Skill tool with `worldagent:scene-simulation`, then read `${CLAUDE_PLUGIN_ROOT}/skills/scene-simulation/references/project-pipeline-and-template.en.md` and `${CLAUDE_PLUGIN_ROOT}/skills/scene-simulation/references/simulation-workflow.en.md`.
2. If the case directory exists and is not empty, stop and ask the user; never delete or reuse its contents. Otherwise write the exact request, verbatim, to a temporary file outside the case and create the case:
   `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/init_case.py <case_dir> --name <name> --prompt-file <request.txt> --simulation-class <class> [--fps N --frame-start A --frame-end B]`
   Use the case directory's basename as `<name>` (letters, digits, `_`, `-` only). Classes: rigid_body, cloth, liquid, gas, particles, granular_approximation, soft_body, coupled; repeat `--simulation-class` for coupled cases. Choose them from the skill's solver classification.
3. Write the world spec into `<case_dir>/manifest.json` (Stage 0): `contract.frame_range`, `contract.fps`, story beats under `contract.story.beats`, one entry per claimed object under `object_contracts`, and the scene graph under `topology`. Follow `${CLAUDE_PLUGIN_ROOT}/schemas/world_spec.schema.json`. If the request states a duration, record it as `contract.story.requested_duration_seconds` and derive `frame_range` from it; the long-form minimum applies only when the request states none (`simulation-workflow.en.md` 1.2). Omit `initial_support` for an object released in free fall (dropped, thrown, or airborne at the first frame). Give every object a `simulation_class` (one of the case classes without coupled, or `fixed` / `kinematic` for objects no solver moves) and the `blender_system` that simulates it (`none` for a plain collider or keyed object). Only the simulated object carries a system (the gas or liquid domain, the cloth, the soft body, the active rigid body, the owner of a simulated particle system); an object that only has a Fluid Flow, Fluid Effector, Collision or force-field role (an emitter, obstacle or collider) is `fixed` or `kinematic` with `none`. A passive or animated rigid body in the rigid body world keeps `bullet_rigid_body`. `systems.physics_roles(obj)` shows an object's roles. Settle these fields now: a change after the spec freezes is a requirement change. Use a preferred system from `${CLAUDE_PLUGIN_ROOT}/schemas/solver_classes.json`; any other needs `solver_choice_reason` with a `reason` and `evidence` (case-relative paths of measured reports), so a new case normally uses the preferred one. Every class an object has, other than fixed and kinematic, must be one of the case's `--simulation-class` values. If objects are simulated by more than one `blender_system`, or the case is `coupled`, also write `topology.solver_graph` (solver and input nodes, one-way edges with a `channel` from `${CLAUDE_PLUGIN_ROOT}/schemas/coupling_channels.json` and `omitted_reactions`, and `bake_order`) and each beat's cross-node effects under `interactions`; see the playbook's coupling section (`material-playbooks.en.md` §7).
   Set each beat's `frame_interval` from a physics estimate of when its event happens (free fall `t = sqrt(2h/g)`, sliding or rolling distance / speed) and leave generous margin on both sides: the windows are frozen with the spec. When an event time is uncertain, suggest one low-resolution probe bake to read the event frames before the first passing spec audit with rows.
4. If `$WORLDAGENT_ASSET_LIBRARY` is set, choose assets from it before planning to build any (library-first). Read its `index.json` if present, otherwise list its folders and each asset's `meta.json`. For every visible object in `object_contracts`, add an entry to a top-level `asset_sources` list in `manifest.json`: `object`, `library_path` (relative to the library, or null), `sha256`, `license`, and `reason`. Use a library asset when its category and real-world size fit the object contract; when none fits, set `library_path` to null and say why. If the variable is not set, skip this step.
5. Write `requirements_matrix`: one row per hard requirement with `id`, `text`, `category` (one of target_asset_realism, scene, physics, story_time, materials, camera, media, delivery), a `pass_predicate` in words with its numbers, status `unknown`, and `covers` naming the beats it verifies (a story row may instead reuse its beat id as its row id). Every beat must be covered. Each row also states what it measures, or the spec audit fails:
   - `tolerances[]` for every distance, penetration, position, or error bound: `quantity`, `basis`, `derivation`, and `value_m` (or `ratio` + `of`). By default `value_m = max(screen_m, solver_m)` with basis `screen` or `solver`: `screen_m` is 5 pixels at the reference resolution at that distance (`5 * worldagent_measure.scale.pixel_footprint(camera, point, resolution)`); the reference resolution is the final render resolution scaled up, aspect ratio kept, until its longer side is at least 1920 px (320x180 uses 1920x1080), `solver_m` the solver's resolution (rigid body collision margin, one grid cell, or cloth/soft body collision distance). Write the calculation in `derivation`. Use basis `request` for a smaller value only when the request asks for that precision; use basis `numeric` with a `ratio` of the object's size for centre of mass or volume; use basis `outcome` for a threshold derived from an outcome the request states (for example "the tower falls over" as top block centre below 0.45 of its start height), with the request clause in `derivation`. An outcome may be looser than the default rule, never tighter: an outcome `value_m` also gives `screen_m` and `solver_m` and is at least their max; a tighter length needs basis `request`.
   - `measures[]` for other compared quantities (speeds, counts, fractions, lower bounds): `quantity`, `comparison`, `value`, and `unit`. A speed threshold states its basis, such as `screen_m x fps`.
   - "Comes to rest" is displacement over a rest window below `screen_m` (`numerical.rest_displacement`, `particles.rest_displacement`), not instantaneous solver speed, which keeps an invisible jitter.
   - No row may contradict what the request makes happen (an object the request covers is not required to stay visible), and no row may ask for what the solver cannot do by construction (Mantaflow total gas density conservation, an SPH pile's angle of repose); record such a limit in the manifest's `approximations` list and tell the user.
   A visual judgement nobody can measure is not a row; review it in the render instead. Follow `${CLAUDE_PLUGIN_ROOT}/schemas/requirements.schema.json`.
6. Run `python3 ${CLAUDE_PLUGIN_ROOT}/bin/spec_audit.py <case_dir>/manifest.json`. It checks the object classes and systems (`simulation_class`, `solver_choice`), the total duration (`duration`), that every row is measurable with a stated tolerance basis (`measurable`, `tolerance_basis`), and that every beat is covered by a row (`beat_coverage`); for a coupled case also the solver graph (`solver_graph_required`, `solver_node`, `solver_edge`, `coupling_disclosure`, `bake_order`, `coupling_support`, `coupling_claim`). Fix every error and run it again until it passes. The first passing run with the matrix freezes the spec and each row's `id`, `pass_predicate`, `tolerances`, and `measures` in `reports/spec_baseline.json`; later changes are listed by the gate and promote for review, so settle the spec with the user before the first passing run where you can.
7. Report the beats, the rows, the asset choices, and the audit result. Say that the case is at status `contract` and not yet verified; describe the audit as passing, never the case as done or complete. Stop here: do not start building until the user agrees with the spec and asks for the bake (`/worldagent:bake <case_dir>`).
