# New WorldAgent case

Arguments: `$ARGUMENTS` — the first word is the case directory; the rest is the user's exact scene request. If either is missing, ask for it.

1. Invoke the Skill tool with `worldagent:scene-simulation`, then read `${CLAUDE_PLUGIN_ROOT}/skills/scene-simulation/references/project-pipeline-and-template.en.md` and `${CLAUDE_PLUGIN_ROOT}/skills/scene-simulation/references/simulation-workflow.en.md`.
2. If the case directory exists and is not empty, stop and ask the user; never delete or reuse its contents. Otherwise write the exact request, verbatim, to a temporary file outside the case and create the case:
   `python3 ${CLAUDE_PLUGIN_ROOT}/scripts/init_case.py <case_dir> --name <name> --prompt-file <request.txt> --simulation-class <class> [--fps N --frame-start A --frame-end B]`
   Use the case directory's basename as `<name>` (letters, digits, `_`, `-` only). Classes: rigid_body, cloth, liquid, gas, particles, granular_approximation, soft_body, coupled; repeat `--simulation-class` for coupled cases. Choose them from the skill's solver classification.
3. Write the world spec into `<case_dir>/manifest.json` (Stage 0): `contract.frame_range`, `contract.fps`, story beats under `contract.story.beats`, one entry per claimed object under `object_contracts`, and the scene graph under `topology`. Follow `${CLAUDE_PLUGIN_ROOT}/schemas/world_spec.schema.json`. Give every object a `simulation_class` (one of the case classes without coupled, or `fixed` / `kinematic` for objects no solver moves) and the `blender_system` that simulates it (`none` for a plain collider or keyed object). Use a preferred system from `${CLAUDE_PLUGIN_ROOT}/schemas/solver_classes.json`; any other needs `solver_choice_reason` with a `reason` and `evidence` (case-relative paths of measured reports), so a new case normally uses the preferred one. Every class an object has, other than fixed and kinematic, must be one of the case's `--simulation-class` values.
4. If `$WORLDAGENT_ASSET_LIBRARY` is set, choose assets from it before planning to build any (library-first). Read its `index.json` if present, otherwise list its folders and each asset's `meta.json`. For every visible object in `object_contracts`, add an entry to a top-level `asset_sources` list in `manifest.json`: `object`, `library_path` (relative to the library, or null), `sha256`, `license`, and `reason`. Use a library asset when its category and real-world size fit the object contract; when none fits, set `library_path` to null and say why. If the variable is not set, skip this step.
5. Write `requirements_matrix`: one row per hard requirement with `id`, `text`, `category` (one of target_asset_realism, scene, physics, story_time, materials, camera, media, delivery), a `pass_predicate` in words with its numbers, status `unknown`, and `covers` naming the beats it verifies (a story row may instead reuse its beat id as its row id). Every beat must be covered. Each row also states what it measures, or the spec audit fails:
   - `tolerances[]` for every distance, penetration, position, or error bound: `quantity`, `basis`, `derivation`, and `value_m` (or `ratio` + `of`). By default `value_m = max(screen_m, solver_m)` with basis `screen` or `solver`: `screen_m` is 5 pixels at the final delivery resolution at that distance (`5 * worldagent_measure.scale.pixel_footprint(camera, point, resolution)`), `solver_m` the solver's resolution (rigid body collision margin, one grid cell, or cloth/soft body collision distance). Write the calculation in `derivation`. Use basis `request` for a smaller value only when the request asks for that precision; use basis `numeric` with a `ratio` of the object's size for centre of mass or volume.
   - `measures[]` for other compared quantities (speeds, counts, fractions, lower bounds): `quantity`, `comparison`, `value`, and `unit`.
   A visual judgement nobody can measure is not a row; review it in the render instead. Follow `${CLAUDE_PLUGIN_ROOT}/schemas/requirements.schema.json`.
6. Run `python3 ${CLAUDE_PLUGIN_ROOT}/bin/spec_audit.py <case_dir>/manifest.json`. It checks the object classes and systems (`simulation_class`, `solver_choice`) and that every row is measurable with a stated tolerance basis (`measurable`, `tolerance_basis`). Fix every error and run it again until it passes. The first passing run freezes the spec in `reports/spec_baseline.json`; later changes are listed by the gate and promote for review, so settle the spec with the user before the first passing run where you can.
7. Report the beats, the rows, the asset choices, and the audit result. Say that the case is at status `contract` and not yet verified; describe the audit as passing, never the case as done or complete. Stop here: do not start building until the user agrees with the spec and asks for the bake (`/worldagent:bake <case_dir>`).
